# Possible Q&A

**Q1. 為什麼用 VLM 而不是訓練一個車損偵測模型（YOLO 等）？**
正樣本只有 53 張，遠不夠訓練；且任務本質是「兩張圖的差異語意判斷」（新損 vs 反光/舊損），不是單圖偵測。VLM 零訓練即達 81% 召回，且輸出可解釋理由。長期規劃（Phase 3）是用複核回寫累積的標註訓練自建輕量模型承接快篩層。

**Q2. 為什麼選 Gemini？跟 Claude/GPT 比過嗎？**
評測 harness 是引擎無關的（同一套配對集、Schema、指標），我們同時寫了 Claude 版腳本。選 Gemini 3.7 Flash 做原型是因為 AI Studio 免費額度讓驗證成本歸零；正式採購時可用同一套 harness 直接對比各家模型的 Recall/FPR/成本再決定。

**Q3. 召回率 86% 不到 90% 目標，怎麼辦？**
141 組逐圖重標後發現：帳面漏抓全部出在照片本身——2 筆借車照拍錯側/未覆蓋損傷部位、4 筆照片過暗或新舊損難辨（含原以為唯一漏抓的 RDH-3092：原圖複驗證實借車照同區已有變形，改判存疑）。對可判定的 137 組，召回率 100%、誤報 0%。也就是說瓶頸不在模型而在拍攝品質，治本靠拍攝端即時檢核與車輛照片鏈。

**Q4. 誤報會不會騷擾用戶？**
不會直接觸及用戶。所有預警先進人工複核，確認才進索賠。且 141 組全量重標後，4 筆帳面「誤報」全數證實是未索賠的真實車損——對重標後的 ground truth，可判定樣本誤報率為 0（138 組中 0 誤報）。

**Q5. 判定不穩定怎麼辦（同一張圖兩次判不同）？**
實測 141 組跑兩輪，140 組判定完全一致（99.3%）；唯一翻轉的是既有舊損密集的臨界案例，這類案件本來就該進人工複核。溫度設 0.1，複核層可再加多數決。

**Q6. 光線、雨天、夜間地下室的照片怎麼處理？**
實測中最極端的案例（白天借車、深夜地下室還車）在 EXIF 轉正後被正確判定。品質檢核層會把過暗/過糊的照片標記「無法比對」走補件，而不是硬判。

**Q7. 隱私與資料安全？**
照片本來就是 iRent 營運資料，存於自家 Azure Blob；送模型判定可走企業版 API（不用於訓練）。照片內容是車體外觀與車內空間，PII 風險低；車牌可在前處理遮罩。

**Q8. 規模化：一天幾千單撐得住嗎？**
判定是非同步批次，不在還車關鍵路徑上。每單 6 次判定、Flash 級單價，全量 2,400 單/日約 NT$1,200；併發用佇列消化，尖峰延遲只影響預警時效（SLA 5 分鐘內仍寬裕）。

**Q9. 使用者亂拍、拍錯角度怎麼辦？**
這正是實測數據支撐的痛點（官方欄位註記「分類常有誤」、後方漏拍 25-30%）。短期：模型輸出 angle_match 擋掉錯配 + 補件流程；治本：二期 App 拍攝端即時檢核，當場提示重拍。

**Q10. 車內整潔分級怎麼驗證？**
已完成首輪實測：自 Blob 抽 80 張（40 筆訂單）跑三級分類，髒汙檢出率 3.75%，髒汙判定經人工看圖抽驗；Pro 複核翻轉了快篩漏判的遺留垃圾案例。下一步擴大到 300 張人工標註建立正式評測集，並修正快篩信心校準（目前「普通」級信心分數偏低導致升級率過高）。

**Q11. 為什麼不在 App 端上模型（on-device）？**
拍攝端檢核（模糊/角度）可以上端側小模型；但借/還比對需要調歷史照片、且要可稽核的判定紀錄，適合雲端。兩者是互補的二期規劃。

**Q12. 成本估算的假設？**
以實測 token 用量（141 組共 349k 輸入/49k 輸出）與公開定價換算，每判定約 2.5k 輸入 tokens；每日 2,400 單假設來自兩日 4,820 單的真實 log。
