# Possible Q&A

**Q1. 為什麼用 VLM 而不是訓練一個車損偵測模型（YOLO 等）？**
正樣本只有 53 張，遠不夠訓練；且任務本質是「兩張圖的差異語意判斷」（新損 vs 反光/舊損），不是單圖偵測。VLM 零訓練即達 81% 召回，且輸出可解釋理由。長期規劃（Phase 3）是用複核回寫累積的標註訓練自建輕量模型承接快篩層。

**Q2. 為什麼選 Gemini？跟 Claude/GPT 比過嗎？**
評測 harness 是引擎無關的（同一套配對集、Schema、指標），我們同時寫了 Claude 版腳本。選 Gemini 3.7 Flash 做原型是因為 AI Studio 有免費額度便於快速驗證（正式成本驗證仍列後續工作）；正式採購時可用同一套 harness 直接對比各家模型的 Recall/FPR/成本再決定。

**Q3. 召回率 85.7% 不到 90% 目標，怎麼辦？**
141 組逐圖重標後發現：帳面漏抓全部出在照片本身——2 筆借車照拍錯側/未覆蓋損傷部位、1 筆照片過暗難辨（另有原以為唯一漏抓的 RDH-3092：原圖複驗證實借車照同區已有變形，經人工定案為無新損，AI 判定正確）。對可判定的 137 組，召回率 100%、誤報 0.85%（1 筆）。也就是說瓶頸不在模型而在拍攝品質，治本靠拍攝端即時檢核與車輛照片鏈。

**Q4. 誤報會不會騷擾用戶？**
不會直接觸及用戶。所有預警先進人工複核，確認才進索賠。且 141 組全量重標、並經 2026-08-30 用戶逐圖複核定案後，4 筆帳面「誤報」中 2 筆確為未索賠的真實車損、1 筆借車照覆蓋不足不可比，僅 1 筆是真誤報（RCG2235 右後把既有痕判為新損）——對重標後的 ground truth，可判定樣本誤報率 0.85%（137 組中 1 筆）。

**Q5. 判定不穩定怎麼辦（同一張圖兩次判不同）？**
實測 141 組跑兩輪，140 組判定完全一致（99.3%）；唯一翻轉的是既有舊損密集的臨界案例，這類案件本來就該進人工複核。溫度設 0.1。

**注意（誠實限制）**：複核層雖然跑 3 票，但實測 4 件升級案全是 3:0 一致、零分歧——在本資料集上多數決**沒有產生可測量效益**，不可宣稱它提升了準確率。級聯的 +4.7pp 完全來自「換用更強模型」。更根本的原因是：同模型家族的第二意見不是獨立意見（reverse_check.py 實測，見下題）。

**Q6. 光線、雨天、夜間地下室的照片怎麼處理？**
實測中最極端的案例（白天借車、深夜地下室還車）在 EXIF 轉正後被正確判定。品質檢核層會把過暗/過糊的照片標記「無法比對」走補件，而不是硬判。

**Q7. 隱私與資料安全？**
照片本來就是 iRent 營運資料，存於自家 Azure Blob；送模型判定可走企業版 API（不用於訓練）。照片內容是車體外觀與車內空間，PII 風險低；車牌可在前處理遮罩。

**Q8. 規模化：一天幾千單撐得住嗎？**
判定是非同步批次，不在還車關鍵路徑上。全量規模約 2,400 單/日、每單數次判定；成本尚未完成正式驗證（實際計價模型與帳單核對列為後續工作），本次不作量化成本宣稱。併發用佇列消化，尖峰延遲只影響預警時效（SLA 5 分鐘內仍寬裕）。

**Q9. 使用者亂拍、拍錯角度怎麼辦？**
這正是實測數據支撐的痛點（官方欄位註記「分類常有誤」、後方漏拍 25-30%）。短期：模型輸出 angle_match 擋掉錯配 + 補件流程；治本：二期 App 拍攝端即時檢核，當場提示重拍。

**Q10. 車內整潔分級怎麼驗證？**
首輪從 Blob 取得 80 張候選影像（40 筆訂單），模型的 `photo_ok` 檢查判定其中 24 張適合進一步做車內整潔判讀、56 張未通過（未納入後續分類統計；人工抽驗 3 張未通過案例，3 張皆為車外照）。級聯模型對 24 張通過檢查影像的分類結果為乾淨 20／普通 1／髒汙 3，髒汙判定經人工看圖抽驗；Pro 複核翻轉了快篩漏判的遺留垃圾案例。目前沒有完整人工 Ground Truth、樣本數也小，下一步擴大到 300 張人工標註建立正式評測集，並修正快篩信心校準（目前「普通」級信心分數偏低導致升級率過高）。

**Q11. 為什麼不在 App 端上模型（on-device）？**
拍攝端檢核（模糊/角度）可以上端側小模型；但借/還比對需要調歷史照片、且要可稽核的判定紀錄，適合雲端。兩者是互補的二期規劃。

**Q12. 成本估算的假設？**
以實測 token 用量（141 組共 349k 輸入/49k 輸出）與公開定價換算，每判定約 2.5k 輸入 tokens；每日 2,400 單假設來自兩日 4,820 單的真實 log。

**Q13. 環節三的通知是真的嗎？**
是，但只有一條管道是真的。人工確認後任務先寫入資料庫，後端再對 `NOTIFICATION_WEBHOOK_URL` 發 HTTP POST（4 秒 timeout），你們看到接收端即時印出 payload；SLA 逾時會再自動發一次升級推播。LINE／簡訊尚未接入，介面標「未接入」，選了只會記錄為 unsupported、不會外發。我們刻意不做假的「已通知」。

**Q14. 派單鎖定有接 iRent 的派單系統嗎？**
沒有，頁面上直接寫「模擬狀態」。目前規則是：有未完成整備任務或手動鎖定就標「整備中・不可派」，完工自動解除。要真的擋單需要派單系統的 API 規格，這是我們無法單方面完成的部分。

**Q15. 站點人員手機版怎麼登入？**
目前已有 Demo 用的 HttpOnly session 登入、Admin／Station RBAC 與後端 ownership 驗證；接單仍由後端以 atomic claim 防止多人搶到同一張單。這不是企業 SSO，Production 仍需正式身分系統、MFA 與更完整的安全控制。

**Q16. 完工照除了存檔還有什麼用？**
它回寫成該車下一次借車比對的基準：監理台「現場實測」可輸入車牌用最近完工照當借車照。這解決的是「借車照品質不可控」這個召回天花板——整備後的照片角度與品質穩定，也讓責任回溯精準到整備完成那一刻。

**Q17. 環節三的資料怎麼存、能規模化嗎？**
任務、事件、發送紀錄、完工照索引都在 SQLite（與監理台同一顆），資料存取層預留 PostgreSQL 方言（DATABASE_URL 切換），Docker 已多階段 build 前端。Postgres 尚未實測，等資料庫 PR 一起驗證。

**Q18. 「營運洞察」的時段分布可信嗎？**
資料是真實上傳 log 4,820 單，但只涵蓋單日（2026-04-22），所以我們只做時段分布、不做星期分布，且頁面標明 n 與日期。它是排班的起點，不是結論。
