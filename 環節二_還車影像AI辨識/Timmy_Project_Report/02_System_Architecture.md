# 系統架構分析

## 整體資料流
```
iRent App（還車 6 張照）
  → Azure Blob carpic/（既有鏈路，零侵入）
  → 事件觸發，非同步入列（不阻塞還車流程）
  → Stage 0 前處理（純 CV，零 API 成本）
      EXIF 方向轉正（實測 76% 照片方向錯置）
      模糊 / 曝光檢核 → 不合格標記「無法比對」成缺圖工單
  → Stage 1 快篩（輕量 VLM，全量）
      借/還同方位配對比對 → 明確無新損（約 85%）直接放行
  → Stage 2 複核（高階 VLM，僅疑似案件 ~15%）
      新損傷？位置 / 類型 / 嚴重度 / 信心 / 判定理由
  → 結構化 JSON → 判定結果 DB
  → 預警引擎（分級路由）
      P1 即時：高信心新損 / 髒汙 → 推播站點客服、車輛暫停派單（SLA ≤5 分）
      P2 工單：疑似 / 無法比對 → 複核佇列（SLA ≤4 小時）
      P3 記錄：正常 → 存檔稽核
  → 複核後台（借/還並排 + AI 理由 + 一鍵裁決）
  → 複核結果回寫 → 標註資料累積 → 持續改善（閉環）
```

## 關鍵設計決策
1. **配對不信任使用者自報分類**：上傳清單欄位官方註記「上傳分類(常有誤)」；以 order_number + ImageType 配對，角度正確性由 VLM 判定時輸出 `angle_match` 校驗。
2. **混合式 = CV 前處理 + 模型級聯**（v1.1 實測修正）：原設計用 ORB 對齊 + SSIM 差異當過濾層，實測 141 組推翻——手持照對齊成功率僅 45%，且差異分數正負樣本完全重疊。CV 退居品質/方向前處理，過濾層改為便宜 VLM 全量快篩 → 高階模型複核。
3. **Structured Outputs**：判定結果強制 JSON Schema（angle_match / new_damage_found / damages[] / pre_existing_notes），下游規則引擎零解析風險；reasoning 欄位讓客服秒懂 AI 為何示警。
4. **AI 是放大鏡不是法官**：所有異常先進人工複核，確認後才進索賠；決定權在營運端。

## 車內整潔分級（F2）
單張判讀三級分類：髒汙（須立即清潔，觸發 P1）/ 普通 / 乾淨。輕量 VLM 初分，「髒汙」與低信心案例升級複核。現有資料無整潔標籤 → 規劃自 Blob 車內照（9,300+ 張）抽 300 張人工標註作校準評測集。
