現況三大痛點

  • 車損責任認定困難：還車後才發現車損時，需人工逐張翻閱借／還車照片比對，耗時且常因照片品質、角度不一致而難以歸責。索賠案例資料顯示，實際爭議多集中在單一方位的細微損傷。
  • 照片品質與分類不可靠：上傳清單欄位即標註「上傳分類(常有誤)」——使用者拍錯角度、分類錯置為常態；後方兩角約 25~30% 訂單直接漏拍，事後根本無圖可比。
  • 車內整潔無人把關：前／後車內照每單皆有上傳（4,700 / 4,644 筆），但目前僅存檔不判讀。髒污車輛流轉給下一位用戶，直接傷害體驗；派員巡檢又成本高。
資料集中已具備天然的驗證樣本：30 台「未索賠」車輛的完整 4 方位借／還配對照（240 張，負樣本），與 28 台「有索賠」車輛的爭議方位配對照（53 張，正樣本）——可直接作為 AI 判定引擎的評測基準。
02

系統目標與功能範圍

F1 · 車外

新車損偵測

以「借車照 vs 還車照」同方位比對，辨識本次租期新增的刮痕、凹陷、破損；既有舊損不誤報。偵測到新車損即產生異常預警。

F2 · 車內

整潔程度分級

辨識前／後車內照，分類為髒汙（須立即清潔）／普通／乾淨三級。判定為「髒汙」時觸發異常預警，優先安排清潔。

F3 · 後台

預警與通知機制

異常事件依嚴重度分級路由：後台工單、即時通知、人工複核閉環，並將複核結果回收為訓練／評測資料。

非目標（本期不做）：損傷金額自動估價、車體 3D 重建、行車中即時偵測。拍攝端檢核中，「品質 Gate（模糊/過暗/過曝擋下重拍）」已實作雛形並實測（見 §04）；「即時角度／完整性檢核」列為第二期擴充（見 §08）。

03

整體系統架構

沿用現行上傳鏈路（App → Azure Blob），以事件驅動方式掛上辨識服務，對既有系統侵入最小。

  • 觸發方式：還車照片組上傳完成（Blob event / 還車 API callback）即入列非同步處理，不阻塞使用者還車流程。
  • 配對邏輯：以 order_number + ImageType（1~4 車外方位、10/11 車內）將本單還車照與同車前一單（或本單借車時）照片配對——不信任使用者自報的分類欄位（實證常有誤），配對後由 AI 於判定時一併校驗角度。
04

混合式辨識 Pipeline

混合式的分工原則：CV 管「看得清楚嗎」，VLM 管「看到了什麼」。傳統 CV 負責便宜且確定性高的前處理與品質把關（EXIF 轉正、模糊/曝光檢核），語意判斷交給 VLM，並以「輕量快篩 → 高階複核」的模型級聯控制成本與誤報。注意：原設計由 CV 擔任「過濾層」，經 141 組實測推翻後改為 VLM 快篩（見本節下方實測修正）。

七步全景：一張還車照片的旅程

F1 · 新車損偵測（借 vs 還 比對）

  • Stage 0 — 品質與方向前處理：EXIF 方向轉正（實測資料集 76% 照片帶未套用的旋轉標記）、模糊度（Laplacian variance）與曝光檢核為純 CV；角度正確性交由 VLM 判定時一併校驗並輸出 angle_match。不合格照片直接標記「無法比對」，成為缺圖工單，而非硬比對產生誤判。
    Quality Gate 實測（quality_gate.py，282 張借還照）：攔下 26 張（9.2%）模糊/過暗照片並給出具體重拍指示——包含唯一連人工都無法複驗的存疑案例 RDZ-0187（清晰度 49、亮度 44，雙重不合格）。若拍攝當下即攔截，判定天花板直接抬高。
  • Stage 1 — 輕量模型快篩：以低價 VLM（Flash 級）對全部配對做第一輪判定，明確「無新損」者直接放行。
  • Stage 2 — 高階模型複核：快篩標記「有新損」或低信心的案件，升級高階模型（Pro / Opus 級）複核後才觸發預警，控制誤報。
實測修正（v1.1）：原設計以傳統 CV（ORB 對齊 + SSIM 差異）作為過濾層，實測 141 組真實配對後推翻——使用者手持拍攝的借/還照角度與光線差異過大，對齊成功率僅 45%，且對齊成功者的差異分數在有損/無損樣本間完全重疊（光影變化淹沒車損訊號）。混合式因此修正為「CV 只做品質/方向前處理，過濾層改用模型級聯」：便宜 VLM 快篩 → 高階 VLM 複核。這也是實測的價值：架構要跟著證據修正。

判定輸出以 Structured Outputs（output_config.format）強制 JSON Schema，下游規則引擎零解析風險：

F2 · 車內整潔程度分級

車內照（ImageType 10/11）為單張判讀、無需借還比對，是典型的三級分類任務——輕量 VLM 做第一線分類，僅「髒汙」判定與低信心（<0.7）案例升級 Pro 級複核，控制誤報又壓低成本。

F2 實測（80 張 Blob 真實車內照，40 筆訂單）：分布為乾淨 21／普通 56／髒汙 3（檢出率 3.75%）。Pro 複核翻轉 5 張，其中 1 張把快篩漏判的「方向盤後方遺留寶特瓶」從乾淨救回髒汙；髒汙判定經人工看圖抽驗，明確污漬案例正確。額外發現：抽樣中即有「車內照」欄位混入車外照（模型誠實回報「非車內照無法判定」）——再次佐證分類錯置為常態，需入補件流程。已知課題：快篩對「普通」級的信心分數校準偏低（中位數 0.1），造成升級率偏高，需在 prompt 明確定義信心語意。

05

後台預警與通知機制

AI 判定不直接對用戶做出裁決——所有異常先進入分級路由與人工複核閉環，AI 是「放大鏡」，決定權在營運端。

事件等級通知路徑SLA
新車損 severity=high 或 confidence≥0.85P1 即時後台紅色工單 + LINE/簡訊推播站點與客服；車輛暫停派單≤ 5 分鐘
新車損 medium/low 或 confidence 0.6–0.85P2 工單後台複核佇列，客服上班時段處理≤ 4 小時

照片缺漏／無法比對（漏拍後方等）P2 工單缺圖清單；App 端推播提醒用戶補拍（二期）當日
判定正常P3 記錄寫入結果 DB，供稽核與抽查—

人工複核閉環

  1. 複核介面並列顯示：借車照、還車照、AI 標註差異框、判定理由（reasoning 欄位讓客服秒懂 AI 為何示警）。
  2. 客服一鍵「確認車損／駁回誤報」；確認後自動帶入照片證據鏈進入既有索賠流程。
  3. 每個複核結果回寫為標註資料——誤報案例進入 few-shot 範例與評測集，形成持續改善迴路（§03 架構圖綠色虛線）。

關鍵發現

  • AI 抓到人工漏掉的車損（標籤噪音）：4 筆「誤報」經逐圖放大複驗——全數確認為真實新車損（RFB5176 藍色擦撞痕+凹陷、RCG2235 反光片旁刮痕、RFH8122 左右後保桿擦痕），只是當時未索賠。「未索賠」≠「無車損」，系統能挽回營運端漏掉的求償機會。
  • EXIF 方向是免費的 +10pp：76% 照片帶未套用的旋轉標記；轉正後召回率 71.4% → 81.0%，並救回「白天借車 vs 深夜地下室還車」的極端光差案例。
  • 剩餘漏抓主因是拍攝覆蓋，不是模型：4 筆 FN 中 2 筆為借車照根本沒拍到損傷部位（模型誠實回報 angle_match=false）；唯一的真誤報也是借/還照拍了不同側所致。治本靠第二期「App 拍攝端即時角度檢核」。

下一步優化（往 Recall ≥90%）

  • ✅ 已實作 — 複核層：快篩「無損但低信心 / 無法比對」升級 gemini-3.1-pro 三票多數決，Recall +4.7pp（85.7%），升級量僅 3%。
  • ✅ 已實作 — Prompt 跨側禁令 / few-shot / 補拍照：跨側誤比型誤報已消除；few-shot 以 8 張「車況回報」特寫為範例（與評測集零重疊）。
  • 車輛照片鏈基準：剩餘 3 筆漏抓中 2 筆是借車照拍錯側／未覆蓋損傷部位——比對基準回溯同車前一單還車照（Blob 依 CarNo 可串）即可治本。
  • ✅ 已實作 — F2 車內整潔首輪實測：80 張 Blob 真實車內照完成三級分類（髒汙檢出率 3.75%，見 §04）；下一步擴大至 300 張人工標註建立正式校準評測集，並修正快篩信心校準。
08

方法論驗證：四次 A/B 與一個反直覺結論

我們沒有只驗證「系統會動」，而是驗證「每一個設計決定是否真的更好」。依一份完整的 Prompt 架構規格重寫判定層，跑滿 141 組真實配對做 A/B——四次全部落敗。 以下是量測過程與結論，含全部負面結果。

★ 最重要的結論：要求模型解釋自己的推理，會讓推理本身變差。
實驗 C 只加了一個欄位——要求模型說明「你憑什麼排除反光／水痕」。它完全不碰任何判定準則， 純粹要求把已經做過的思考寫出來，結果 Recall 掉了 13.7pp。 合理推測：強迫為每筆痕跡產出「排除理由」，等於誘導模型去論證「這是真損」， 於是對本該低調處理的模糊痕跡也編出說詞（誤報 +3），同時把注意力從「比對」移到「說明」（漏抓 +3）。

因此本系統的可解釋性一律由判定之後的層產生（規則表理由、客服說明）， 而不是在判定當下要求模型自我解釋。這正是估價與文案層是純加分、而四次 prompt 改寫全部落敗的分野。

幻覺長什麼樣子：逐張看圖複驗

四次實驗的誤報不是「判斷偏鬆」，而是高信心杜撰。我們對每一筆都調出原圖人工複驗。 以 RDL7827-左前 為例（三個不同版本的 prompt 都在這張照片上編出同樣的損傷）：

模型輸出 · confidence 0.92
「還車照中左前輪後方至車門下緣的側裙處可見大範圍塑膠件破裂、斷裂外翻與立體變形， 邊緣撕裂不規則並向上突起；借車照中該處線條平整完好。」
人工調圖複驗 · 事實
該處完好無損。輪拱下方為斜角視角下的陰影，模型把陰影與輪拱輪廓幻覺成結構性破裂， 並主動聲稱借車照該處乾淨以強化敘事。
為何這是最危險的失敗模式
敘述具體、位置明確、信心 0.92——客服看不出破綻，會直接對用戶開單求償。 能靠信心門檻過濾的誤報不可怕，可怕的是這種。實測門檻掃描確認：要把誤報壓到 0%， Recall 得從 100% 崩到 63.6%，沒有任何操作點優於現行版本。

規格門檻為何不可照抄：1,476 筆實測分布

規格要求「上次沒拍清楚的部位不得對用戶主張」，並設定基準照觀測品質 ≥0.8 才可自動處置。 我們對全部 141 張借車照逐分區評分，得到 1,476 筆觀測品質——

<0.5　13%
0.5–0.65　22%
0.65–0.8　64.9%
不得主張 信心折損 可用 規格認定「可自動處置」＝ 0.1%（2/1,476）

※ 規格的門檻預設基準照是「營運人員入隊時的高品質完整拍攝」；本資料集是用戶手持手機拍攝， 觀測品質中位數 0.65、最大值僅 0.75。照抄規格＝自動處置永遠不會發生。

連帶推翻的第二個預設：相乘式加權在數學上不可用。 規格的「偵測信心 × 基準品質」因 prior_q 上限 0.75，乘積永遠 ≤0.74，達不到 0.85 的自動處置門檻—— 27 筆偵測全數降級（含 21 筆確認真損），只擋到 1 筆誤報。改為兩道獨立門檻 （信心 ≥0.85 且 品質 ≥0.70）後，自動處置從 0 件回到 13 件，保護語意完全保留。
誠實限制：本資料集上這層降了 9 筆真損、抓到 0 筆誤報——它沒有提升準確率。 其價值是結構性的：用戶申訴時能證明「借車照確實拍得到該部位」。

估價不交給模型
