## 一、目前做到哪

用真實營運照片實測完成一套 AI 車況判讀系統：

| 成果 | 數字 |
|---|---|
| 新車損偵測（借/還照比對，141 組人工逐圖重標） | **召回 95.5%、誤報 0%** |
| 自動分流 | 自動放行 83%・自動預警 15.6%・**需人工僅 1.4%** |
| 判讀成本 | 每單 < NT$1；原型驗證全程 **$0**（Gemini 免費額度） |
| 亮點案例 | 從「未索賠」樣本抓出 4 筆真實車損；photo-chain 跨訂單抓到 RDE-0180 新損並鎖定責任訂單 |
| 資料品質發現 | 70% 車內照欄位其實是車外照；76% 照片 EXIF 方向錯置——佐證環節一必要性 |

已實作的加值功能：**車輛損傷護照**（36 台損傷歸戶＋責任訂單）、**Quality Gate**（純 CV 攔模糊/過暗照）、**部位定位**（17 類 enum）、**Cleanliness Score**（可解釋計分）、**photo-chain**（跨訂單責任回溯）。

### 資料規模的正確講法（別講錯）
- 上傳清單 xlsx 涵蓋 **27,367 張照片、4,820 筆訂單、3,121 台車**（2026-04-22～23 兩日），每張都附 Azure Blob 網址
- 但**主辦方打包的本機照片只有 293 張**（索賠 53＋未索賠 240）；我們的 141 組借還配對評測就是用這 293 張
- 額外自行從 Blob 下載：80 張車內照（F2）、photo-chain 掃描用的跨訂單照片
- 資料集涵蓋兩日 27,367 張上傳紀錄；標註打包的車損樣本 293 張，配成 141 組做全量人工重標評測

### 為什麼是 Gemini VLM 而不是傳統 CV
技術路線是 **Gemini VLM（Vision Language Model，視覺語言模型）級聯**：gemini-3.7-flash 全量快篩 → 臨界 2.8% 升級 gemini-3.1-pro-preview 三票多數決。

但我們**原本的設計是傳統 CV 當過濾層**（ORB 特徵點對齊 → SSIM 差異分數 → 有嫌疑才送 VLM），先實作 CV 那層並實測 141 組，結果被自己的數據推翻（`cv_prefilter.py` / `cv_results.json`）：

| CV 前濾實測 | 結果 |
|---|---|
| 借還照對齊成功率 | **64/141 = 45%** |
| 差異分數（有車損 vs 無車損）中位數 | 11.79 vs 11.36 —— **完全重疊、無鑑別力** |
| 21 組有車損樣本中通過對齊者 | 只有 3 組（最需要判斷的案例上失效最嚴重） |

原因：使用者手持拍攝，借還照的角度、距離、光線落差過大，光影變化造成的差異淹沒了車損訊號。

**重點：CV 沒有被丟掉**，只是換了位置——EXIF 方向轉正（+10pp 召回）與 Quality Gate（攔模糊/過暗 9.2%）仍是純 CV。**便宜、確定性高的工作留給 CV，需要語意理解的判斷交給 VLM**。被換掉的只有「過濾層」。

## 二、環節二的系統架構

### 主線：一張還車照的旅程

```
使用者 App 上傳還車照 ──→ Azure Blob（沿用既有鏈路，對現行系統零侵入）
                              │ 事件觸發，非同步處理，不阻塞還車流程
                              ▼
  ① 影像前處理      EXIF 方向轉正 + 壓縮至 1280px       純 CV      run_eval_gemini.py: prep_image()
                    └─ 76% 照片方向錯置，轉正後召回 +10pp
                              ▼
  ② 品質檢核 Gate   模糊 / 過暗 / 過曝 → 當場請用戶重拍  純 CV      quality_gate.py         攔 9.2%
                    └─ Laplacian 變異數測清晰度、亮度直方圖測曝光；單張 <50ms、零 API 成本
                              ▼
  ③ 借還照配對      訂單 × 方位，配出同方位的借車照      程式        build_pairs.py
                    └─ 不信任使用者自報的分類欄位（官方註記「常有誤」），方位由 AI 於判定時校驗
                              ▼
  ④ 快篩判定        借還比對 + 方位校驗 + 新損偵測       Flash      run_eval_gemini.py      全量
                    └─ gemini-3.7-flash，低單價全量跑
                              ▼
  ⑤ 級聯複核        臨界案例升級，三票多數決             Pro        run_cascade.py          2.8%
                    └─ gemini-3.1-pro-preview。升級條件：判無損但信心<0.7／判有損但信心<0.85／方位不符
                              ▼
  ⑥ 結構化輸出      pydantic schema 強制 JSON            —          Assessment
                    └─ 下游規則引擎零解析風險
                              ▼
  ⑦ 風險分流        P1 / P2 / P3 路由                    程式規則    分流門檻
                    └─ 自動放行 83%・自動預警 15.6%・需人工 1.4%
                              ▼
        車況監理台（案件複核 / 損傷護照 / 營運總覽）──→ 人工複核結果回寫為標註資料
```

**分工原則：CV 管「看得清楚嗎」，VLM 管「看到了什麼」。** ①②③⑥⑦ 是純程式／CV，零 API 成本；只有 ④⑤ 需要付費 API。

### 支線功能（都掛在主線輸出上）

| 支線 | 做什麼 | 技術 | 腳本 |
|---|---|---|---|
| **F2 車內整潔** | 單張判讀分三級（髒汙/普通/乾淨） | Flash 快篩 → Pro 複核（髒汙或信心<0.7） | `classify_interior.py` |
| **整潔計分** | AI 盤點問題（11 類 × 3 級程度）→ 程式端加權扣分 0–100 | Flash + 程式規則 | `cleanliness_score.py` |
| **視覺標註** | 損傷位置圈框（box_2d 正規化座標）＋中文說明 | Flash | `annotate_damage.py` / `batch_annotate.py` |
| **部位定位** | 損傷歸到 17 類固定部位 enum | Flash | `part_tagger.py` |
| **損傷護照** | 損傷歸戶到「車」＋首次發現訂單＝責任歸屬 | 程式彙整 | `build_passport.py` |
| **護照感知判定** | 判定時附上既有損清單，AI 只找「護照之外的新東西」 | Flash | `passport_judge.py` |
| **Photo-chain** | 比對基準改用同車前一單還車照，責任回溯到單 | Flash | `photo_chain.py` |

### 判定的結構化輸出（`Assessment` schema）

```json
{
  "angle_match": true,              // 借還照是否同方位，false 則走補件流程
  "new_damage_found": true,
  "damages": [{
    "location": "左後葉子板",
    "type": "刮痕",                  // 刮痕 | 凹陷 | 破損 | 掉漆
    "severity": "medium",           // low | medium | high
    "confidence": 0.87,
    "reasoning": "借車照同位置無此線狀痕跡，非反光（跨兩個鈑件連續）"
  }],
  "no_damage_confidence": 0.0,      // 判「無新損」時的把握程度，級聯升級看這個
  "pre_existing_notes": "右下保桿既有舊損，兩照皆存在，不列新損"
}
```

`reasoning` 欄位是給客服看的——AI 不只給答案，還要說出為什麼，這是可解釋性的核心。

### 三個關鍵設計決策（會被評審問）

1. **零侵入接入**：不改 App、不改上傳流程，掛在 Blob 事件後面非同步處理。導入成本低、風險可控。
2. **模型級聯而非單一模型**：便宜模型全量跑、貴模型只看臨界案例（2.8%）。實測級聯讓召回 +4.7pp、判定穩定性 99.3%，成本卻幾乎沒增加。
3. **AI 是放大鏡，不是法官**：所有異常都進人工複核閉環，AI 不對用戶直接裁決；每次複核回寫成標註資料，形成持續改善迴路。

> https://claude.ai/code/artifact/ab616929-dda5-47a6-9324-8cb6d022c6d2
> 本機備份在 `artifacts/irent-ai-architecture.html`

## 四、Dashboard（車況監理台）怎麼開

三個分頁：**營運總覽**（KPI＋判讀流水線動畫＋車隊損傷熱點）、**案件複核**（借/還照同步放大鏡＋AI 標註框）、**車輛損傷護照**（3D 車模＋部位表格）。

### 方式 A：單檔版（最簡單，demo 保底）
直接雙擊這個檔案，或：
```bash
open "環節二_還車影像AI辨識/dashboard/irent-review-dashboard.html"
```
零依賴、離線可用，照片資料全部內嵌。複核動作只存在自己瀏覽器。

### 方式 B：Server 版（多人共享複核＋AI 現場重判）
```bash
cd 環節二_還車影像AI辨識/dashboard
uvicorn server:app --host 0.0.0.0 --port 8000
```
開 http://localhost:8000 ；同網路隊友連 `http://<開server那台的IP>:8000`。
- 複核決策存 SQLite **全隊共享**（每 5 秒自動同步）
- 案件頁有「⟲ AI 重判」按鈕：現場呼叫 Gemini 重新判定（約 10 秒，需 `.gemini_key`）
- ⚠️ 資料含真實車牌，**只能跑 localhost／隊內區網，禁止部署公網**

### 改了東西要重組
- UI 改 `dashboard/dashboard_shell.html`（單檔版與 server 版共用同一份模板）
- 資料改 `pipeline/` 下的 JSON
- 然後 `python3 dashboard/build_dashboard.py` 重新產生單檔版；server 版打 `POST /api/reload` 或重啟即可

### 6.2 隊友 A：把實測「做深」——擴大證據與案例
主軸：現有結論建立在 141 組上，把樣本與案例擴大，讓數字更有底氣、demo 故事更多。

**A1. Photo-chain 擴大掃描（★最高 CP，建議先做）｜半天～1 天**
- 現況：1,126 台車有跨訂單車外照，**只掃了 15 台**就抓到 RDE-0180 的跨單新損（右後保險桿刮痕，3 票一致＋人工目檢證實、且不在索賠清單上）
- 做法：`cd pipeline && python3 photo_chain.py --sweep 100`（免費額度 RPM 8，100 台約 1.5 小時，可中斷續跑）
