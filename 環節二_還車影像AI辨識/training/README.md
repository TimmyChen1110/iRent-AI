# 自訓 CV 模型：流程驗證

> **結論先講：目前訓出來的模型遠不如現行 VLM 級聯，不應接入主流程。**
> 這個資料夾的價值在於**把整條路打通並誠實量測**，等監理台累積足夠標籤後可直接重跑。

## 為什麼要做這件事

VLM API 判定準確、上線快，但長期而言自訓模型在成本與延遲上更有優勢。
問題從來不是「訓不訓得出來」，而是**標註資料**。
本次實作驗證了整條 pipeline，並用實測數據回答「現在還差多少」。

## 實測結果（5-fold 車輛分組交叉驗證）

| 指標 | 本模型 | 現行 VLM 級聯 |
|---|---|---|
| ROC-AUC | **0.594**（隨機 = 0.50） | — |
| PR-AUC | 0.218（隨機 = 0.159） | — |
| Recall | 45.5% @ FPR 22.4% | **95.5% @ FPR 0%** |

**ROC-AUC 0.59 代表模型只比隨機猜好一點點。** 現行 VLM 完勝。

### 診斷：不是程式問題，是資料量問題

- 訓練 loss 降到 0.06，驗證卻只有 0.59 → 典型過擬合
- Ablation：凍結 backbone 只訓最後一層（linear probe）得 **0.611**，
  略優於全微調的 0.594 → 進一步佐證瓶頸在樣本量，不在訓練設定
- 22 個正樣本不足以學到泛化特徵
- 車損是**細粒度局部特徵**（刮痕常只占畫面極小面積），
  224px 全圖分類先天不利——這也是未來要改用局部裁切/高解析度輸入的理由

## 方法論上的三個關鍵決定

**1. 以「車輛」分組切分，不是以照片。**
同一台車有 4 個方位，若按照片隨機切，同車照片會同時出現在 train 與 val，
模型可以靠「認得這台車」得到虛高分數。這是小資料集最常見的洩漏來源。

**2. 類別不平衡用加權而非重採樣。**
正樣本僅 15.9%，用 `pos_weight` 加權 BCE；在 22 筆正樣本上做重採樣會嚴重過擬合。

**3. 看 PR-AUC / Recall@FPR，不看 accuracy。**
全部猜「無車損」就有 84.1% accuracy——accuracy 在這個任務上完全沒有意義。

## ⚠️ Demo 時的重要提醒

`predict.py` 對**訓練集內**的照片會給出近乎完美的機率（實測 0.96 / 0.06），
**那是記憶不是泛化**。唯一誠實的指標是 out-of-fold ROC-AUC 0.59。
請勿用訓練集照片佐證模型效果。

## 用法

```bash
source ../.venv/bin/activate

python3 build_dataset.py          # 組資料集（relabels + 監理台裁決）
python3 train_classifier.py       # 5-fold 車輛分組交叉驗證
python3 train_classifier.py --export   # 交叉驗證後全量重訓並匯出權重
python3 predict.py 還車照.jpg      # 單張推論
```

資料來源自動合併，監理台累積的裁決會優先採用：

```
pipeline/relabels.json        141 組人工重標（目前唯一來源，138 筆可用）
dashboard/decisions.sqlite3   監理台複核裁決（上線後持續累積）
```

## 什麼時候該重跑

以本資料集流量估算（4,820 單/日 × 4 方位 ≈ 19,280 組/日），
車損率 0.5% 時約 **52 天**可累積 5,000 正樣本。建議里程碑：

| 正樣本數 | 可做什麼 |
|---|---|
| < 100 | 僅流程驗證（**現在在這**，22 筆） |
| 100–1,000 | 二分類可試訓，觀察 ROC-AUC 是否隨資料量上升 |
| 1,000–5,000 | 分類模型可能達可用水準；偵測模型仍不足 |
| 5,000+ | 可訓偵測模型（需先人工修框） |

**關鍵訊號**：資料量翻倍時 ROC-AUC 有沒有明顯上升。
若有，繼續蒐集；若停滯在 0.6 附近，代表任務本身需要換方法
（借還照雙流比對、局部裁切、更高解析度），而不是繼續加資料。
