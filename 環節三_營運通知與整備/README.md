# 環節三：營運通知與車輛整備流程

> 目標：設計流程與機制，讓客服及營運人員可以**即時得知車況**（車輛清潔或車損），安排後續車輛整備及清潔。

## 狀態：任務閉環已實作（監理台整備看板）＋ 整備中心管理者介面第一期已實作，通知管道未接

### 已完成（程式碼在 `backend/`，隨監理台一併交付）

- **複核後台**（38 個真實案例、可上台操作；server 版 `backend/app/server.py`）
  - P1 即時預警／P2 工單／P3 記錄三級**分級標記**，紅橙綠色條佇列
  - 借/還照並排 + AI 標註框（直接圈出損傷/髒污位置）+ 判定理由
- **整備任務閉環（2026-09-05 實作）**：
  - 一鍵裁決「確認車損／確認髒汙」→ 自動建立維修／清潔任務（SQLite `tasks` 表，冪等防重複開單）
  - 監理台「整備看板」分頁：待處理 → 處理中 → 已完成 Kanban、指派人員、完成時間、`task_events` 處理歷程
  - 復原裁決自動取消待處理任務；`GET/PATCH /api/tasks` 完整 API；19 項零 API 成本回歸測試
- **整備中心管理者介面 第一期（2026-09-14 實作）**：`frontend-admin/`（React + Vite + motion）→ build 至 `backend/app/static/ops/`，由監理台 server 於 **http://localhost:8000/ops** 提供；API 為 `backend/app/ops_api.py`（`/api/ops/*`）+ `ops_db.py`，規劃見 `UI_規劃.md`
  - 通知中心：事件流（由 `task_events` 增量派生）、未讀／已讀（依自選身分）、KPI、篩選
  - 整備看板：三欄拖曳／按鈕推進（同一套狀態機）、SLA 倒數、負責人／類型／逾時篩選
  - 任務詳情（側板）：借還照 + AI 標註框、工作內容、通知狀態與重發、處理歷程與備註
  - 人員與組別、通知設定（管道狀態只回布林、SLA 門檻可調）
  - SLA 逾時自動產生事件（P1 5 分／P2 4 小時／P3 當日，待處理→開工）；15 項回歸測試 `tests/test_ops.py`
- **三對象通知文案生成**（`pipeline/notify.py`）：用戶通知／客服摘要／派工單文字 + 程式面 grounding 查核——**只生成文案，不會發送**
- **預警分級與 SLA 設計**（架構文件 §05，僅設計）：P1 ≤5 分鐘通知站點/客服、P2 ≤4 小時工單、缺圖案件當日補件清單

### 待完成（以下皆尚無程式碼，不得在 Demo 中宣稱已有）
