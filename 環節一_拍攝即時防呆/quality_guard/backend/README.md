# iRent Photo Quality Guard — 環節一（四階段拍照防呆）

拍照即時防呆：使用者上傳/貼上一張車輛照片後，系統回傳**車牌號碼**、**拍攝角度**，
以及不合格時的**具體重拍原因**。

設計背景見上層目錄 `irent_photo_quality_guard_plan.md`，四階段整合的施工圖見
`../整合計畫_四階段辨識.md`（本文件即該計畫完成後的成果說明）。

## Pipeline：對外三關（闖關式，前一關沒過就不跑下一關）

API 對外呈現三個關卡（`stages` 欄位），是把內部五個階段合併過的：

```
上傳照片
  ├─ 第 1 關  基本可讀性 ── 內部 Stage 0 + Stage 1
  │     能否解碼、解析度、整張有沒有內容 → IMAGE_INVALID / LOW_RESOLUTION
  │     模糊/亮度只計算並標註「偏暗」「偏模糊」，**預設不擋關**
  ├─ 第 2 關  車牌偵測 ──── 內部 Stage 2（YOLO best.pt + fast-plate-ocr）
  │     偵測位置 → 讀出號碼 → 檢查字數（字數不對＝車牌只拍到一半）
  │     → PLATE_NOT_FOUND / TOO_FAR / TOO_CLOSE / PLATE_TEXT_UNREADABLE
  │       / PLATE_INCOMPLETE
  └─ 第 3 關  四角辨識 ──── 內部 Stage 3 + Stage 4（MobileNetV2 四分類）
        → WRONG_VIEW / UNCERTAIN_VIEW
```

三關全過才算合格。每一關在 `stages` 裡的狀態是 `passed` / `failed` / `skipped`，
並附一句可直接顯示的 `summary`（例如「車牌 RCG-2235（辨識信心 99.4%）」）。
前端照著 `stages` 畫三張卡片即可，不需要自己從錯誤碼反推是哪一關失敗。
`stages` 永遠是完整三筆，不會因為提早結束就少給。

三個刻意的設計決定：

- **闖關式，前一關沒過就不跑後面。** 一張全黑或解析度過低的照片硬跑三個模型，
  得到的也只是垃圾輸出加一堆衍生錯誤；使用者也只需要知道「現在卡在哪一關」。
- **第 1 關只擋解析度，不擋模糊/亮度。** 整張照片的平均亮度不能代表「車牌讀不讀得到」
  ——夜間停車場的照片整體很暗，但車牌有反光板，往往比車身還清楚。能不能用交給第 2 關
  實際偵測，第 1 關只把「偏暗」「偏模糊」標註出來當參考。詳見下方實測。
- **關卡內部不提早結束。** 第 1 關的模糊與亮度各自獨立，一次跑完一起回報，
  使用者不用重拍兩次才知道照片同時又暗又糊。
- **第 3 關即使沒過，也要把判定結果講出來。** 判不出來（`UNCERTAIN_VIEW`）或判得
  跟指定角度不符（`WRONG_VIEW`）時，仍然顯示模型當下的判定與信心值——那是使用者
  決定要怎麼重拍的依據。

> **可切換**：`QualityThresholds.run_view_stage_when_plate_missing`（預設 `False`）
> 設成 `True` 時，第 2 關沒過仍會跑第 3 關。實測沒偵測到車牌的 81 張真實照片，
> 視角分類仍有 **91.4%** 正確率（有偵測到車牌的是 97.0%），所以那不是在賭運氣，
> 純粹是產品要「闖關」還是要「一次把知道的都講完」的取捨。

## ⚠️ 最重要的一件事：raw_data 檔名的「車頭左右」是錯的

**模型輸出即正確答案，不要在程式裡「修正」它的左右。**
`app/view_taxonomy.py` 的 `VIEW_CLASS_NAME_TO_REQUIRED_VIEW` 是直接對應；
需要修正的是**驗證真值**那一側，由 `validation/parse_filename.py` 負責。

### 為什麼

`raw_data` 的照片檔名（例如「RCG2235左前 借.jpg」）在**車頭照**上把左右寫反了。

幾何證明：車頭正對鏡頭時，駕駛座（左駕、位於車子左側）會出現在畫面右邊；攝影者要
往自己左邊移動，才會露出車子的**右**側——此時畫面上會是「車頭在右、車身往左延伸」。
實際檢視三台不同車輛的「左前」照片（RCX5100、RDG8578、RCQ6760）全部符合這個特徵，
也就是畫面裡其實都是車子的**右前角**；「RCG2235右前」則相反，是左前角。

推測成因：App 要使用者「去車子左前方拍」，使用者面對車頭站到自己的左邊就按下快門，
檔名記的是 **App 要求的欄位**，不是畫面裡實際拍到的角度。車尾照沒有這個問題——拍車尾
時攝影者跟車子同向，兩邊左右一致，實測車尾標註也確實正確。

交叉驗證：`scripts/check_dataset_label_convention.py` 把人工目視分類過的訓練資料集
（`~/Desktop/和泰黑客松/dataset/`）比對回原始照片（相關係數 1.0 的完全比對，次佳僅
0.3~0.6，不會配錯）。修正檔名真值之後，**183/186 張一致（98.4%）**，剩下 3 張是零星
個案而非系統性差異：

| 修正後真值 \ 資料集資料夾 | 左前 | 右前 | 左後 | 右後 |
|---|---|---|---|---|
| 左前 | **48** | 1 | 0 | 0 |
| 右前 | 2 | **48** | 0 | 0 |
| 左後 | 0 | 0 | **42** | 0 |
| 右後 | 0 | 0 | 0 | **45** |

### 踩過的坑（別再踩一次）

早期版本反過來做：把 raw_data 檔名當成真值，於是在 `view_taxonomy.py` 加了一張把
車頭兩類左右對調的表。那樣做驗證分數看起來很漂亮（因為在跟錯的真值對答案），但
**實際上把模型正確的輸出翻成了錯的**，使用者上傳車子右前角的照片會看到「左前」。

判斷原則：**模型學的是人工目視標註的資料集，那一邊是對的；檔名是產線欄位，不是標註。**
如果 `check_dataset_label_convention.py` 回報不一致，先檢查 `parse_filename.py` 的
修正表，不要去動模型輸出。

⚠️ **驗證分數抓不到這個 bug。** 當時模型輸出被翻錯、驗證真值也是錯的，兩個錯誤互相
抵消，`view_accuracy` 一樣是 96.9%；修正兩邊之後還是 96.9%（只有左前/右前的分項數字
互換）。這類「座標系定義」的錯誤只能靠實際看畫面或幾何推理抓，不能靠準確率數字。

## 快速開始

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

.venv/bin/uvicorn app.main:app --reload --port 8000
.venv/bin/python -m pytest tests/ -q          # 另開終端機
```

前端（純靜態）：

```bash
cd frontend && python3 -m http.server 5500
# 瀏覽器開 http://localhost:5500（後端要先跑在 8000）
```

手機測試時後端要用 `--host 0.0.0.0` 啟動，前端會自動用同一個 host 組 API 網址。

`GET /healthz` 會回報兩個模型的載入狀態（`ok` / `degraded`），模型載入失敗不會讓
服務起不來——Stage 0/1 的純 CV 檢查仍然可用。

### 方向與取景：手機直拍 vs 橫拍

這一版處理的是「使用者怎麼拿手機」造成的兩個獨立問題。兩者都不需要另外訓練一個
模型——四角類別講的是「車相對鏡頭的姿態」，跟照片本身是直是橫無關。

**問題一：內容橫躺的照片（方向）。** 285 張真實照片裡有 **30 張（10.5%）**檔案是
直的、但內容是橫拍，要轉 90 度車子才會正。這種照片對車牌偵測器是致命的——它只
見過正立車牌，橫躺時幾乎完全測不到，使用者會拿到「未偵測到車牌」然後怎麼重拍
都一樣。`checks/orientation.py` 用兩段式判斷把它們救回來：

| 判斷 | 用什麼訊號 | 實測（98 張 val） |
|---|---|---|
| 要不要轉 90 度 | YOLO 車牌偵測信心值（橫躺時測不到） | 橫躺判對 98.8%；正立誤判 1.1% |
| 順轉還是逆轉 | OCR 讀不讀得出合法 7 碼（顛倒的讀不出來） | 92.4% |

**只有第一次偵測失敗才會啟動**，所以正常照片完全不多花錢；啟動時最多多兩次 YOLO
推論（約 47ms/次）。⚠️ 拿視角分類器自己的信心值去挑方向是行不通的，實測只有
59.2% 猜對、套下去準確率從 0.990 掉到 0.745，理由寫在 `orientation.py` 的 docstring。

**問題二：橫幅取景（長寬比）。** 舊的 `Resize(256) → CenterCrop(224)` 保留的畫面
範圍取決於原圖長寬比：直立圖保留 100% 的寬度，16:9 橫幅**只剩中間 49%**——而判斷
四角關係的線索多半就在被裁掉的左右兩端。改成 letterbox（補邊成正方形）之後：

| 取景情境 | 舊版 CenterCrop | 新版 letterbox |
|---|---|---|
| 原始取景（直拍為主） | 0.990 | 0.990 |
| 橫幅 16:9 | 0.888 | **0.949** |
| 橫幅 4:3 | 0.959 | **0.980** |
| 直式 9:16 | 0.990 | 0.990 |

**問題三（訓練/推論錯位，順手修掉）**：`ImageFolder` 的 PIL loader 不套 EXIF，但
推論端的 `cv2.imdecode` 會套。第一/二版因此有 293/578 張（51%）訓練樣本是橫躺著
餵進模型的，推論時卻永遠拿到正立圖。改用 `load_image_upright` 當 loader 修正。

前處理現在集中在 `checks/view_preprocess.py`，訓練腳本與推論服務 import 同一份；
checkpoint 多存一個 `preprocess` 欄位，載入時照它建對應的 transform，舊的 .pt
會自動退回舊前處理。**前處理不一致的失敗是無聲的**（模型照樣回一個看起來正常的
機率分布，準確率卻悄悄掉幾個百分點），所以不要在別處另外抄一份 transform。

### 第 1 關為什麼不擋模糊/亮度

原本第 1 關會用整張照片的平均亮度與 Laplacian 清晰度擋關。實測發現這會誤殺：
**被舊規則擋掉的 39 張真實照片裡，有 12 張的車牌其實讀得完全正確**——夜間停車場的
照片整體偏暗，但車牌有反光板，往往比車身還清楚。用「整張照片的亮度」去否決一張
車牌清晰可讀的照片，判斷的根本不是我們在乎的東西。

改成不擋關之後：

| | 改之前 | 改之後 |
|---|---|---|
| 過第 1 關 | 246/285（86.3%） | 285/285（100%） |
| 判定合格 | 126 張 | 141 張 |
| 其中車牌讀對 | 120 張（95.2%） | 132 張（**93.6%**） |

多救回 12 張讀對的，代價是多放行 3 張讀錯 1 個字元的。合成劣化測試也支持這個取捨：
把照片調暗到 0.25 倍後，通過的照片裡 48% 車牌讀對、只有 5% 讀錯；調亮的則是 50% 讀對、
0% 讀錯——會通過的多半是「暗歸暗，車牌照樣讀得出來」。

模糊/亮度仍然會計算，結果標註在第 1 關的結論裡（例如「平均亮度 13%（照片偏暗，仍繼續
判讀車牌）」），只是不擋關。要改回擋關就把 `QualityThresholds.stage1_blocks_on_blur`
或 `stage1_blocks_on_brightness` 打開，門檻值都還在。

### 車牌字數檢查（`PLATE_INCOMPLETE`）

第 2 關除了「有沒有找到車牌」，還會檢查**讀出來的字數對不對**——字數不足代表車牌的
頭或尾被畫面邊緣裁掉了。這條規則的效益在真實資料上非常明確：

| OCR 讀出字數 | 張數 | 完全讀對 |
|---|---|---|
| 7 碼 | 131 | **125（95%）** |
| 非 7 碼 | 34 | **0（0%）** |

非 7 碼的內容典型長這樣：`RDG857`、`RDR635`、`RDH226`（尾碼被裁）、`FH8052`、
`JG8578`（首碼被裁）。加上這條規則後：

| | 加規則前 | 加規則後 |
|---|---|---|
| 判定合格 | 155 張 | 126 張 |
| 其中車牌讀對 | 120 張（77.4%） | 120 張（**95.2%**） |

**擋掉的 29 張全部都是車牌讀錯的，讀對的一張都沒少**——在這批資料上是零誤擋成本。
合法字數設定在 `QualityThresholds.plate_text_valid_lengths`（預設 `{7}`）。
⚠️ 台灣還有 6 碼車牌（`1234-AB`、`AB-1234`），這批車隊沒有；若之後納入這類車輛，
要改成 `frozenset({6, 7})`，否則那些車會被永久擋住。

### 為什麼 pass 率從 73.3% 掉到 55.8%？這是變好不是變壞

舊 pipeline 的「81.1% 車牌偵測率」是傳統 CV 找「長得像車牌的區域」，文字精確辨識率
是 0%——也就是幾乎都不是真的車牌，卻讓照片通過。現在改用真的偵測器之後，
**69 張 `PLATE_NOT_FOUND` 抽樣檢查後發現絕大多數是車牌真的被裁到畫面邊緣外**，
那正是這套防呆系統存在的理由。舊的高 pass 率是假的：舊版 73.3% 的合格照片裡，
車牌文字正確率是 0%；現在 55.8% 的合格照片裡有 92.5% 車牌讀對。

## 門檻值怎麼校準的

`app/config.py` 每個門檻都標了依據，兩類要分清楚：

- **已用真實資料校準**：模糊、亮度、車牌面積比例、OCR 信心值。
  例如 `plate_area_ratio_min = 0.005` 不是取分位數，而是看「OCR 從哪裡開始讀不出來」：
  面積比例 <0.005 的樣本 OCR 正確率 0%，0.005–0.008 是 50%，>0.012 才穩定在 8 成。
- **尚未校準**：`plate_area_ratio_max`（真實照片最大只到 0.077，這條規則一次都沒觸發過）、
  `view_confidence_min = 0.6`（真實照片的 top-1 機率中位數 0.999、p10 0.972，
  這個門檻在真實資料上幾乎不會觸發，需要蒐集「模型該不確定」的樣本才校得動）。

改動 `app/checks/` 底下任何演算法後請重跑驗證：

```bash
.venv/bin/python -m validation.run_validation
```

真實照片來源優先用 `quality_guard/raw_data/`，沒有的話自動退回 repo 內的簡報資料夾
（293 張原始照片本來就在那裡），也可以用 `IRENT_RAW_DATA_DIR` 覆寫。

## 已知限制（demo 時要主動說明）

- **車牌文字辨識 56.1% 不代表模型只有五成**：分母包含車牌被裁掉、只拍到局部的照片。
  真正該看的是「判定合格的照片裡車牌讀對的比例」＝ 92.5%——那才是這套系統實際交付
  給下游的品質。
- **室內視角（前車內/後車內）完全沒有驗證資料**：293 張真實照片全部是車外四角，
  室內視角只跑 Stage 0/1，Stage 2-4 直接略過，實際效果未經驗證。
- **`view_confidence_min = 0.6` 在闖關模式下幾乎不會觸發**：能走到第 3 關的照片
  代表車牌已經完整入鏡、構圖正常，分類器對這種照片幾乎永遠很有信心
  （top-1 中位數 0.999），包含它答錯的時候——這條防線擋不住「模型很有信心地答錯」。
  它真正有用的場景是打開 `run_view_stage_when_plate_missing` 之後：對車牌沒入鏡、
  只拍到局部的照片會觸發 11 次。
- **車外/車內 heuristic（Tier A）不擋關**：對已知全是「車外」的 285 張照片誤判率 28.8%，
  只放在 `debug.exterior_interior_guess` 供參考。
- **視角分類器對車頭照的左右仍是相對弱項**（右前 85.7% 是四類中最低，左前 97.8%、
  車尾兩類 95.1/97.8%）。訓練腳本的註解已說明這是資料量問題，要改善靠擴充資料
  而不是加模型容量。
- **新版模型不再容忍橫躺的輸入**：整張圖轉 90 度時準確率只有 32.7%（上一版是 87.8%）。
  上一版那份容忍度是 EXIF bug 的副產物——51% 訓練樣本橫躺換來的——而同一個 bug 也
  正是它橫幅取景表現較差的原因。現在改由 `checks/orientation.py` 在 Stage 2 保證
  送進分類器的圖是正立的，這條路徑依賴車牌偵測成功，而闖關流程本來就要求先過
  第 2 關才會跑第 3 關，所以正常流程下分類器不會拿到橫躺的圖。
  ⚠️ 但若把 `run_view_stage_when_plate_missing` 打開，車牌沒偵測到的照片方向就
  沒被確認過，橫躺的那些會有約 35% 機率被很有信心地答錯（`view_confidence_min`
  只擋得下其中 49%）。試過用 90 度旋轉增強讓模型自己抗旋轉，只把 32.7% 拉到 46.9%，
  卻讓橫幅 16:9 從 94.9% 掉到 91.8%——不划算，所以維持交給防護網處理。
- **順轉/逆轉判斷有 7.6% 會選錯**：選錯的結果是圖上下顛倒，OCR 會讀出錯的車牌號碼
  （實測 285 張裡出現過 1 張，讀成 `2LSS000`）。這種照片原本是直接 `PLATE_NOT_FOUND`，
  現在會變成「讀到一個錯的車牌」。要更保守可以在 `orientation.py` 的挑選邏輯上
  加一條「兩個方向都讀不出合法 7 碼就不轉」。

## 目錄結構

```
app/
  main.py                  FastAPI app（lifespan 載入三個模型）、POST /api/photo-quality/check
  schemas.py               API 的 Pydantic 請求/回應模型
  config.py                門檻值 + 模型檔案路徑（含每個數值的校準依據）
  view_taxonomy.py         六分類 + 模型類別↔RequiredView 對照表（直接對應，勿加左右修正）
  models/view_classifier.pt  四角分類模型 checkpoint
  checks/
    blur.py                模糊檢查
    brightness.py          亮度檢查
    plate_yolo.py          Stage 2：YOLO 車牌偵測 + fast-plate-ocr（單例、吃 ndarray）
    orientation.py         Stage 2：方向防護網（偵測不到車牌時試著轉正再測一次）
    framing.py             遠近判斷（車牌面積比例 + 找不到車牌時的平滑色塊訊號）
    view_classifier.py     Stage 3：MobileNetV2 四角分類（單例）
    view_preprocess.py     視角分類的前處理（**訓練與推論共用，不要另外抄一份**）
    view.py                車外/車內 heuristic（advisory only）
    quality_rules.py       四階段整合、提早結束、錯誤碼與文案
validation/
  parse_filename.py        從檔名解析真值（並修正車頭左右寫反的問題）
  run_validation.py        真實照片 + 合成劣化，輸出準確率報表
scripts/
  check_dataset_label_convention.py  資料集標籤 vs 修正後真值的一致性比對
  train_view_classifier.py           四角分類器訓練
  classify_tool.py                   單張分類的本機測試小工具
tests/                     pytest（沒有模型檔時會 skip 需要模型的測試）
```
