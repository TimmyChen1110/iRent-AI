> ### 後續補做（2026-09-09）：手機直拍 vs 橫拍
>
> 這份計畫預設所有照片都是正立的，實際上不是。後續補了三件事，數字見
> `backend/README.md` 的「方向與取景」一節：
>
> | 問題 | 做法 |
> |---|---|
> | 285 張真實照片裡有 30 張內容橫躺，卡在 `PLATE_NOT_FOUND` | 新增 `checks/orientation.py`：Stage 2 偵測不到車牌時，用 YOLO 判「軸」+ OCR 判「順逆」把圖轉正再測一次。偵測率 64.2% → 74.7% |
> | 橫幅取景的左右兩端被 `CenterCrop` 裁掉（16:9 只剩中間 49% 寬度） | 前處理改 letterbox 補邊；橫幅 16:9 準確率 0.888 → 0.949 |
> | 訓練端 PIL loader 不套 EXIF、推論端 `cv2.imdecode` 會套，51% 訓練樣本橫躺 | 訓練 loader 改 `load_image_upright`；前處理集中到 `checks/view_preprocess.py`，訓練與推論共用 |
>
> ⚠️ 修好 EXIF 之後模型失去了原本「意外」的旋轉容忍度（橫躺輸入 87.8% → 32.7%），
> 改由方向防護網保證送進分類器的圖是正立的。這個取捨與它的風險寫在
> `config.py` 的 `run_view_stage_when_plate_missing` 註解。

> 另外修掉一個計畫沒預料到的量測問題：加了跨階段提早結束之後，被 Stage 1 擋下的照片
> 根本沒送進 YOLO，舊的「車牌偵測率」分母把它們算成偵測失敗。`run_validation.py`
> 的分母已改成「真的跑到 Stage 2 的張數」，並新增 `blocked_rate_after_degradation`
> 區分「有沒有攔下」與「有沒有用預期的錯誤碼攔下」。

> 這份文件給接手整合工作的 agent／工程師讀。目標是把 `quality_guard/`（拍照品質檢查）、
> `../app_models/`（隊友的 YOLO 車牌偵測 + fast-plate-ocr）、以及本次新加入的視角分類模型
> （`quality_guard/backend/app/models/view_classifier.pt`）接成一條完整 pipeline。
> 三者目前都各自能跑，但彼此沒有接線——這份計畫就是接線的施工圖。

## 目標流程（擋關順序，前面沒過就不跑後面，省運算）

```
上傳照片
  │
  ├─ Stage 0：基本可讀性
  │    圖片能不能正常解碼、是不是全黑/全白 → 不行就直接擋
  │
  ├─ Stage 1：影像品質（現有 blur.py / brightness.py，很快、不用等模型）
  │    模糊 → 擋 IMAGE_BLURRY
  │    太暗/過曝 → 擋 TOO_DARK / TOO_BRIGHT
  │
  ├─ Stage 2：車輛與車牌偵測（接隊友的 bbox 模型，取代現有 plate.py 的 OCR heuristic）
  │    沒偵測到車牌 → 擋 PLATE_NOT_FOUND
  │      （這一步本身就會順便擋掉「正側面」「沒拍到車」「太遠看不到車牌」）
  │    車牌 bbox 面積比例太小/太大 → 擋 TOO_FAR / TOO_CLOSE
  │
  ├─ Stage 3：視角分類（我們訓練的 CNN，只有前面都過了才會跑到這裡）
  │    分類成左前/右前/左後/右後
  │    跟 required_view 不符 → 擋 WRONG_VIEW
  │
  └─ Stage 4：信心值防線（不是新 label，是機率門檻）
       如果 4 類的最高機率 < 門檻（例如 0.6）→ 擋 UNCERTAIN_VIEW，
       提示「無法確認角度，請重新拍攝」
```

## `view_classifier.pt` checkpoint 格式（重要，別重寫成別的格式）

這個 `.pt` 不是單純的 `state_dict`，是一個 dict，載入方式照抄 `classify_tool.py`：

```python
checkpoint = torch.load(MODEL_PATH, map_location="cpu")
classes = checkpoint["classes"]              # 四個類別名稱的 list，順序即 softmax 輸出順序
image_size = checkpoint["image_size"]        # transforms.CenterCrop 用
normalize_mean = checkpoint["normalize_mean"]
normalize_std = checkpoint["normalize_std"]
state_dict = checkpoint["state_dict"]
```

`classes` 是「左前/右前/左後/右後」四個中文字串（實際順序以 checkpoint 裡存的為準，
不要憑印象重新硬編碼順序）。模型架構是 `torchvision.models.mobilenet_v2(weights=None)`
+ 換掉最後一層 `classifier[-1]` 成 `nn.Linear(in_features, len(classes))`，跟
`train_view_classifier.py` 的 `build_model()` 一致。

## Stage 3 施工細節：把 `view.py` 換成訓練好的分類器

1. 新增類似 `classify_tool.py` 開頭那段的模型載入邏輯（建議放
   `app/checks/view.py` 或新檔 `app/checks/view_classifier.py`），FastAPI 啟動時載入一次。
2. 新增函式例如 `classify_corner(image_bgr) -> CornerClassification`，回傳
   `label`（四選一字串）+ `confidence`（top-1 機率），直接對應 `checkpoint["classes"]`
   的其中一個值，不需要再拆成現有的 `side` / `front_rear` 兩個欄位（那是舊 heuristic
   的產物，新模型是直接四分類，介面可以簡化，但要同步改 `schemas.py` 的
   `DebugInfo`／`PhotoQualityCheckResponse`）。
3. `required_view` 目前的型別在 `app/view_taxonomy.py`（`RequiredView`），確認它的四個
   值跟 `checkpoint["classes"]` 的字串是同一套命名，不一致要建一個對照表，不要假設兩邊
   剛好字串相同。
4. Tier A（車外/車內）heuristic 不必動，繼續放 debug、不擋關（既有理由：285 張真實

## Stage 4 施工細節：信心值門檻

1. `app/config.py` 的 `QualityThresholds` 新增 `view_confidence_min: float`（初始值先猜
   0.6，之後跑 `validation/run_validation.py` 對真實照片實測校準，比照 `plate_min_score`

2. `quality_rules.py` 新增錯誤碼 `WRONG_VIEW`（分類結果跟 `required_view` 不符）與

## 重構 `quality_rules.py`：明確分階段、提早結束

現在的 `run_quality_check()` 是「全部檢查都跑過一輪、收集所有 errors」，跟這次要的
「Stage 0 沒過就不跑 Stage 1」不一樣。改寫時：

- 前面 stage 沒過，後面 stage 直接跳過（省掉 YOLO/OCR/分類器的運算時間），但
  `debug` 欄位裡沒跑到的項目就是 `None`，不要因為拿不到值而報錯。
- 保留現在「先跑完所有平價檢查（Stage 0/1）」的設計，不要為了「一有錯就中斷」把
  Stage 1 內部的模糊/亮度也拆成互斥——那兩個各自獨立判斷、互不影響，可以一起跑完再一次
  回報，只有跨 stage（1 → 2 → 3 → 4）才需要提早結束。
